# 設計書 — 首都圏 鉄道新線計画シミュレーター

最終更新: 2026-10-31（M0 初版）。実装に合わせて随時更新する。
数値はすべて `src/config/` に外出しし、本書の値は「初期値」の説明である。**（仮置き）** と書いた値は根拠が弱く、M4/M5 で見直す。

## 1. 目的とスコープ

- ユーザーが描いた新線について「日平均乗客数」「営業収支（黒字/赤字）」「建設費の回収年数」を数秒以内に推計して返す。
- 精度目標: 既存駅の乗降客数を対数スケールで概ね再現（目安: 対数 R² ≥ 0.6、中央値の誤差倍率 ≤ 1.6 倍）。
  ゲームとしての「もっともらしさ」と挙動の単調性（駅を増やす・都心に近づける等の操作に対して直感どおり動く）を優先する。
- Phase 1 では運行本数・種別は固定。既存線の需要変化は扱わないが、型とモジュール境界は用意しておく（ロードマップは §8）。

## 2. アーキテクチャ

### 2.1 モジュール構成と依存方向

```
core  ←  data, network  ←  demand  ←  finance  ←  state  ←  ui
```

| モジュール | 責務 | 主な型 / 関数（予定） |
|---|---|---|
| `core` | ドメイン型、幾何計算 | `Zone`, `ExistingStation`, `UserLine`, `DemandResult`, `FinanceResult`, `distanceKm` |
| `data` | `public/data/*` の読込と型付け、メッシュコード変換、空間インデックス | `loadZones()`, `loadExistingNetwork()`, `meshBounds()`, `GridIndex` |
| `network` | エディタ状態の操作（純粋関数）、スナップ、区間延長、新線＋既存の統合グラフ | `addStation()`, `moveVertex()`, `snapToExisting()`, `buildLineGeometry()`, `NetworkGraph` |
| `demand` | 需要推計（四段階の各段を別インターフェースで分離） | `CatchmentModel`, `TripEndModel`, `DistributionModel`, `AssignmentModel`, `runDemand()` |
| `finance` | 建設費、収入、経費、キャッシュフロー | `estimateConstruction()`, `estimateAnnual()`, `buildTimeline()` |
| `config` | パラメータ（出典コメント付き）と校正結果 JSON | `demandParams`, `costParams`, `serviceDefaults` |
| `state` | アプリ状態ストア、変更通知、localStorage 保存、JSON 入出力、再計算のデバウンス | `Store`, `saveScenario()`, `importScenario()` |
| `ui` | MapLibre レイヤー、エディタ操作、結果パネル、Chart.js | — |

- `demand` と `finance` は DOM / MapLibre に依存しない純粋関数とし、vitest で単体テストする。
- 計算が重くなった場合は `demand`+`finance` をそのまま Web Worker に移せるよう、入力・出力は構造化複製可能なプレーンオブジェクト（`Map` は可）にする。

### 2.2 データフロー（実行時）

```
UserLine 編集 ──▶ state（debounce 300ms）──▶ runDemand(scenario, baseData, params)
                                              │   1. 駅勢圏・駅選択（Huff）

```

### 3.2 加工済みデータの形式（`public/data/`）

GitHub の制限（1ファイル 100MB、推奨 50MB 未満）と初回ロード時間を考慮し、1ファイル数 MB 以内を目標にする。

- `zones.json` — 列指向 JSON。形状は持たずメッシュコードから復元する（`src/data/meshCode.ts`）。
  ```json
  { "version": 1, "meshLevel": "half", "code": [533946111, ...], "pop": [1234, ...], "emp": [567, ...] }
  ```
  実績（M1）: 49,522 メッシュ（うち対象地域内 46,703）、0.89MB。`inRegion` 列で対象地域内/外周バッファを区別。
- `region.geojson` — 対象地域の外形（200m 簡略化、73KB）。
- `rail_lines.geojson` — 既存路線（路線ごとに 1 フィーチャ、座標は小数 5 桁 ≒ 1m、10m で簡略化）。属性は `id`（network.json の路線添字）・路線名・事業者・事業者種別。
- `stations.json` — 駅グループの配列（`ExistingStation` 型の元データ）。位置、路線添字、事業者、`inRegion`、乗降集計クラスタ `cluster`、S12 観測値 `ridership`（2019/2024 年度）、`partial`（一部事業者のデータ無し）、`includesShinkansen`。`calibrate.py` が `acc`（ACC）・`mass`（集中量 M）・`catch`（駅勢圏 X）・`muCatch`（駅勢圏由来の乗降推計）を追記する。
- `times.bin` — 既存駅間の最短所要時間（分、上三角の uint8、255 = 到達不能）。`calibrate.py` の出力。
- `network.json` — 既存ネットワーク。`lines`（路線名・事業者・表定速度の初期値）、`edges`（`[駅a, 駅b, 路線添字, 線路延長m]`）、`walk`（名前の異なる近接駅間の徒歩乗換 `[駅a, 駅b, 直線距離m]`）。所要時間は実行時に「延長 / 表定速度」で計算する（速度を設定で変えられるように）。経路探索は（駅, 路線）を状態とし、路線を変えると乗換抵抗を加える。
- `landprice.json` — 地価ポイント `[lng, lat, 円/m², 用途区分]` の配列（任意）。

#### 駅グループと乗降集計クラスタ
- **駅グループ**: N02 のグループコード（同名かつ 300m 以内の事業者別駅をまとめたもの）。需要モデル（Huff・分布）の「駅」はこの単位。
- **乗降集計クラスタ**: S12 で「他路線駅に記載（重複コード 2）」の行がある場合、その駅グループと記載先の駅グループを 1 クラスタにまとめる（例: JR 武蔵小杉の横須賀線ホーム）。校正ではクラスタ内の推計値の合計を観測値と比べる。観測値はクラスタの代表駅（ID 最小）にのみ持たせる。

#### 表定速度（`scripts/config/pipeline.yaml` の `rail.speed_kmh`、**仮置き**）
JR 在来線 40、民営 35、公営 30、第三セクター 40、東京メトロ 30、つくばエクスプレス 55、路面電車 15、モノレール・新交通 27 km/h。急行・快速は考慮しない。M4 で代表区間の時刻表所要時間と照合する。

#### N02 の路線名に関する注意
路線名は法令上の線名で、運行系統とは一致しない（例: 山手線の東京〜田端は「東北線」）。同一事業者の線名をまたぐ直通運転にも乗換抵抗がかかってしまうため、M4 では「同一事業者内の乗換抵抗」を他社間より小さくする（またはゼロにする）設定を設ける。

## 4. 需要推計エンジン（Phase 1）

### 4.1 全体像と四段階推定との対応

| 四段階 | Phase 1 の実装 | 将来の拡張 |
|---|---|---|
| 発生・集中 | 駅勢圏（Huff 按分後）の人口・従業者数から駅別トリップ端数を推計（§4.4、既存駅で校正） | ゾーン別の発生・集中モデル（PT 原単位、目的別） |
| 分布 | 新線駅＋接続駅の外部ポータル間の対称重力モデル（§4.5） | 全駅間（全ゾーン間）重力モデル、PT OD での校正 |
| 分担 | Huff の「鉄道を使わない」外部選択肢と都心距離による分担率の変化（§4.2） | 手段別所要時間を用いたロジットモデル |
| 配分 | 新線上の経路は一意 → 区間別の累積で断面輸送量（§4.6） | ネットワーク全体の経路選択（確率的配分）、既存線への影響 |

各段は `src/demand/` で別インターフェースとし、`runDemand()` が順に呼ぶ。
Phase 2 以降は段単位で実装を差し替える（例: `DistributionModel` を全ネットワーク版に交換）。

### 4.2 駅勢圏と駅選択（外部選択肢付き Huff モデル）

記号: ゾーン $i$（人口 $P_i$、従業者 $E_i$、都心距離 $D_i$）、駅 $s$（既存駅グループ＋新駅。接続駅にスナップした新駅は既存駅と同一視）。

- アクセス距離 $d_{is} = \lambda \cdot \mathrm{dist}(i, s)$（$\lambda$: 迂回係数 1.25 **（仮置き）**）。$d_{is} > d_{\max}$（2.0km）の駅は選択肢から除外。
- アクセス抵抗 $f(d) = \exp(-\beta d)$。
- 駅の魅力度 $A_s = \mathrm{ACC}_s^{\,\alpha}$（§4.3。ネットワーク上で多くの目的地に早く行ける駅ほど選ばれる）。
- 鉄道を使わない選択肢の効用 $V_{0,i} = \exp(a_0 + a_1 D_i)$（郊外ほど自動車・バス等が選ばれやすい＝**鉄道分担率が都心距離で低下**する効果を表す）。

ゾーン $i$ の住民・従業者が駅 $s$ を利用する確率:

$$\pi_{is} = \frac{A_s f(d_{is})}{V_{0,i} + \sum_{k} A_k f(d_{ik})}$$

**既存駅のすぐ横に新駅を置いても過大にならない理由**: 既存駅が近くにあるゾーンでは分母がすでに大きく $\sum_s \pi_{is} \approx 1$ に飽和しているため、新駅は既存駅から利用者を奪うだけで総量はほとんど増えない。さらに新駅の $A_s$ が既存駅（多路線・都心直結）より小さければ、取り分も小さい。駅の空白地帯では分母が $V_{0,i}$ に支配されるため、新駅で鉄道利用が純増する。

駅勢圏人口・従業者: $\tilde P_s = \sum_i \pi_{is} P_i$, $\tilde E_s = \sum_i \pi_{is} E_i$

### 4.3 ネットワーク・アクセシビリティ（ACC）

駅 $s$ から鉄道ネットワークで到達できる「集中ポテンシャル」の総和:

$$\mathrm{ACC}_s = \sum_{m \ne s} M_m \exp(-\gamma\, t_{sm})$$

- $t_{sm}$: 既存ネットワーク上の最短所要時間 [分]（乗車時間＋乗換抵抗。急行は考慮しない）。`calibrate.py` が全駅間（1,619×1,619）を Dijkstra で求め、
  整数分に丸めて `public/data/<地域>/times.bin`（上三角の uint8、約 1.25MB）に書き出す。校正もブラウザも同じ丸めた値を使う。
- 乗換抵抗: 同一事業者の路線間 3 分、他事業者間・新線との乗換 8 分（**仮置き**）。名前の異なる近接駅は徒歩で結ぶ。
- $M_m$: 駅 $m$ の集中量。循環を避けるため、駅の魅力度を使わない幾何的な按分で求める:
  $M_m = \sum_i (E_i + \psi P_i) \cdot \frac{f(d_{im})}{\sum_k f(d_{ik})}$（$\psi = 0.3$、**仮置き**）
- 新線ありの所要時間（`src/demand/newNetwork.ts`）: 既存駅 $o$ が接続駅 $k$ で新線に乗るコストを $b_k(o) = t_{ok} + \tau$（$o = k$ なら $\tau$ なし）とすると、
  - 既存→既存（新線経由）: $t^{\text{via}}_{od} = \min_{k \ne l} b_k(o) + T_{kl} + b_l(d)$
  - 既存→新駅: $\min_k b_k(o) + T_{kn}$、新駅→新駅: $T_{nm}$
  - $T$ は新線上の乗車時間（延長 / 表定速度 40 km/h、**仮置き**）。
- 新線ありの ACC は、各組の所要時間を $\min(t^{\text{old}}, t^{\text{via}})$ に置き換えて計算する。接続駅が無い孤立路線は既存駅に到達できず ACC が小さいため、需要もほぼ生じない。

### 4.4 発生・集中（駅別トリップ端モデル）

駅 $s$ の 1日平均乗降人員（トリップ端数）:

$$\ln \mu_s = c_0 + \eta \ln X_s + \theta \ln(\mathrm{ACC}_s / 10^6) \quad\left(X_s = \tilde P_s + \rho \tilde E_s\right)$$

- 校正時のみ $\kappa \ln(\text{路線数})$ を加える（S12 が乗換客を含めて数えることを吸収するため）。新線の推計では使わず、乗換は §4.5 で明示的に計算する。
- 新駅: 上式そのもの。
- 既存駅: 校正時の推計値 $\mu^{\text{cal}}_s$（`stations.json` の `muCatch`）を、駅勢圏と ACC の変化率で補正する:
  $\mu_s = \mu^{\text{cal}}_s (X^{\text{new}}_s / X^{\text{cal}}_s)^\eta (\mathrm{ACC}^{\text{new}}_s / \mathrm{ACC}^{\text{old}}_s)^\theta$。
  新線で到達性が上がった駅では発生量が増え（誘発需要）、新駅に駅勢圏を取られた駅では減る。

### 4.5 分布と経路選択

全駅（既存駅＋新駅）を発地とする発生制約型の重力モデル

$$T_{o \to d} = \frac{\mu_o}{2} \cdot \frac{M_d\, e^{-\gamma t_{od}}}{\mathrm{ACC}_o}$$

のうち、新線を通る流動だけを新線の OD として集計する（`src/demand/distribution.ts`）。

- 新駅が発着する流動: すべて新線を使う。既存駅側の端は最も早い接続駅で乗り換える。
- 既存駅どうしの流動: 新線経由の割合を 2 項ロジット $s = 1 / (1 + e^{\lambda (t^{\text{via}} - t^{\text{old}})})$ で与える（$\lambda = 0.3$/分、**仮置き**。新線経由が 5 分速いと約 82%）。
  これにより「既存線の利用者が新線を短絡路として使う」流動（環状線・短絡線の需要）を扱う。新線経由が既存経路より 20 分以上遅い組は計算を省く。
- 発地側・着地側それぞれから求めた流動を半分ずつ足して対称化する（往復で同じ量）。
- 輸送人員の内訳: 両端とも新線の駅勢圏＝「新線内」、片方が既存線方面＝「既存線と乗継」、両端とも既存線方面＝「既存線からの経路転換」。

**設計からの変更（M4）**: 当初は「新線の駅＋接続駅ごとの外部ポータル」の対称重力モデル（反復比例法）と、接続駅の近傍に限った短絡利用を考えていた。
全駅間の所要時間行列をブラウザに持たせると、既存網のどの駅との間でも新線経由の時間を直接比べられる。そのため、ポータル間の重複計上の問題がなくなり、短絡利用も同じ式で扱えるので、こちらに変更した。

### 4.6 配分と出力

- Phase 1 の新線は 1 本の線で経路が一意 → OD を区間に積み上げて方向別の断面輸送量を得る（`src/demand/assignment.ts`）。
- 駅別乗降人員 = 当該駅を発着する新線の流動の合計。駅勢圏の利用者（`fromCatchment`）と乗換客（`fromTransfer`）に分ける。
- 輸送人キロ = $\sum T_{xy} \cdot L_{xy}$（新線区間のみ）。
- 新規鉄道利用人口 = 駅勢圏の鉄道利用確率 $\sum_s \pi_{is}$ の増分 × 人口（既存駅の横に新駅を置いても増えないことの確認に使う）。
- 出力型は `DemandResult`（`src/core/types.ts`）。

### 4.7 計算量

新駅・接続駅から 2km 以内のゾーンだけで Huff を再計算し、所要時間は全駅の組（約 260 万）× 接続駅の組で調べる。実データで 1 回 約 80ms（20 駅程度、接続駅 3）。
編集中は 300ms デバウンスし、メインスレッドで計算する（重くなれば `src/demand` をそのまま Web Worker に移す）。

### 4.8 既知の簡略化

- 駅選択（Huff）は目的地を考えずに行うため、大きな既存駅のすぐ横の新駅では、本来は既存駅から乗る目的地の利用者まで新線に乗せてしまう（過大側）。
- 既存駅の集中量 M は新駅に取られる分を差し引かない。
- 新線開業による既存線の混雑緩和・所要時間変化は扱わない（既存網の所要時間は固定）。

## 5. 校正

### 5.1 データ

- 目的変数: S12 の駅別 1日あたり乗降客数。2024 年度を主とし、コロナ前の 2019 年度でも推定して比較する（2024 年度の合計は 2019 年度の約 90%）。
- 集計単位は乗降集計クラスタ（§3.2）。重複コード=1 かつ データ有無=1 の行だけを合計し、二重計上を除く。
- 除外: 観測値なし、`partial`（一部事業者のデータ無し）、`includesShinkansen`（東京・上野・大宮・熊谷）、外周バッファ内の駅。除外した駅とその理由は一覧に残す。

### 5.2 手法: ポアソン疑似最尤法（PPML）＋外側の非線形最適化

- 線形部分（$c_0, \eta, \theta, \kappa$）は対数リンクのポアソン GLM（`statsmodels`、頑健標準誤差 HC1）。
- 非線形パラメータ（$\beta, \alpha, a_0, a_1, \rho, \gamma$）は、内側の GLM 逸脱度を目的関数として Nelder–Mead（境界付き）で外側から最適化する（profile likelihood）。
- **推定範囲の制約（M4 で決定）**: 制約なしの最適解は α≈25・a₁<0・γ≈0.009 と行動として不自然で、新駅の位置を少し動かすだけで需要が極端に変わる。
  そのため α ≤ 2、a₁ ≥ 0、γ 0.02〜0.15/分 などの範囲で推定した。結果、α・a₁・γ は範囲の端に張り付いている（駅単位の乗降データだけでは識別しきれない）。
  鉄道分担率の都心距離による変化は a₁ ではなく、駅密度と ACC（郊外ほど小さい）を通じて表れている。

**PPML を選ぶ理由**（対数線形 OLS ではなく）:
1. 対数 OLS は誤差の分散が平均に依存すると水準の予測が系統的に偏る（再変換バイアス）。収入は水準で効くため致命的。
2. PPML は平均の関数形が正しければ分布の仮定なしに一致推定量になる（Santos Silva & Tenreyro, 2006）。過分散があっても点推定は一致し、標準誤差は頑健化で対応できる。
3. 乗降客数は数百〜数百万人と桁が大きく異なり、ゼロ近傍の小駅も扱える。

懸念: PPML は大規模駅の重みが大きい。大ターミナルの影響を見るため、(a) 全駅、(b) 上位ターミナル除外 の 2 通りで推定して比較する。

### 5.3 評価と出力（`docs/calibration.md`）

- 係数・標準誤差、逸脱度ベースの疑似 R²、対数スケールの R²、RMSE（人/日）、誤差倍率の中央値
- 空間ブロック（2次メッシュ単位）での 5-fold 交差検証の指標（過学習の確認）
- 残差（対数比）の大きい駅 上位 30 件と考えられる原因
- 推定パラメータから計算した「暗黙のトリップ原単位・鉄道分担率」と PT 調査値との比較

### 6.2 建設費

建設費 = Σ 構造別 km 単価 × 延長 ＋ Σ 構造別 駅単価 × 駅数 ＋ 用地費 ＋ 車両費（開業時点に一括計上）

| 項目 | 地平 | 高架 | 地下 | 根拠 |
|---|---|---|---|---|
| 線路 km 単価（駅除く） | 40 億円/km | 100 億円/km | 300 億円/km | 地下は METRO・CAO に合わせて設定。地平・高架は**仮置き**（宇都宮LRT 47億円/km、TX 約161億円/km を参考） |
| 駅単価 | 10 億円 | 40 億円 | 200 億円 | 地下は METRO から逆算。地平・高架は**仮置き** |
| 用地幅 | 12 m | 10 m | 0（用地費なし） | **仮置き** |

- 駅の構造は、隣接する区間のうち最も高価な構造（地下 > 高架 > 地平）とする。
- 接続駅（既存駅にスナップ）は既存駅の改良として駅単価 × 0.7（**仮置き**）。
- 用地費 = 用地幅 × 延長 × 地価 × 補正係数 1.0（**仮置き**）。駅（接続駅を除く）は 3,000m² を追加。
  地価は地価公示（L01）の**住宅地**の地点から逆距離加重（近い 4 地点、半径 3km）で推定する。近くに住宅地の地点がなければ他の用途を使う。
  駅前の商業地の価格を線路全体に当てはめると過大になる（試算で約 2 倍）ため。
- 車両費 = 必要編成数 × 編成両数 × (1 + 予備率 10%) × 1.5 億円/両（E235）。必要編成数 = ⌈ピーク時運行本数 × 往復所要時間 / 60⌉、往復所要時間 = 走行時間 × 2 + 折返し 10 分 × 2。
- 検算（地下）: 有楽町線延伸の条件で 2,320 億円（実際 約2,690 億円、−14%）、南北線延伸で 1,090 億円（実際 約1,310 億円、−17%）、相鉄・東急直通線で 3,400 億円（実際 約2,900 億円、+17%）。

### 6.3 運賃収入

- 1 トリップの運賃 = max(平均賃率 × 新線の乗車キロ, 平均最低運賃)。乗換客も新線区間の運賃を別に払う（別会社の加算運賃と同じ扱い）。
- 平均賃率 = 定期外賃率 × (1 − 定期の割合 × 定期割引率) = 18 × (1 − 0.6 × 0.57) ≒ **11.8 円/人キロ**。
  MLIT-R4 の関東大手民鉄 8 社の（定期外＋定期）運賃収入 / 輸送人キロは 約 10〜13.5 円（平均 約11.8円）。
  収入に占める定期の割合（東急 約39%）と、人キロに占める定期の割合 60%（**仮置き**）から定期外 18 円・定期割引 57% とした。
- 最低運賃 150 円（**仮置き**、大手民鉄の初乗りの水準）にも同じ係数を掛けて平均値とする。
- 年間収入 = 日平均（年平均日）の収入 × 365。平日・休日の人数は表示用に、平日 245 日・休日 120 日・休日係数 0.70（**仮置き**）で年間合計が一致するよう按分する。

|---|---|---|
| 運行本数 | 片道 120 本/日（ピーク 12 本/h）、6 両編成 | **仮置き** |
| 運転費＋車両保存費 | 140 円/車両キロ | MLIT-R5: 関東大手民鉄 8 社 118〜166 円（中央値 約140円）、東京メトロ 約214円 |

| 管理費など | 上記合計の 35% | MLIT-R5: 保守管理・輸送管理・案内宣伝・厚生福利・一般管理費 / それ以外の営業費 = 33〜43% |

### 6.5 収支・回収年数

- 営業収支 = 年間収入 − 年間運行経費（**減価償却前**、諸税・支払利息も含まない）。黒字/赤字の判定もこれで行う。
  （回収年数で建設費を回収するので、減価償却費を経費に含めると二重計上になるため。UI では「減価償却前」と明記する。）
- 需要の立ち上がり: 開業 1〜5 年目の需要係数 0.70 / 0.80 / 0.90 / 0.95 / 1.00（**仮置き**）。収入にだけ掛ける（運行は開業時から定常）。
- 単純回収年数 = 建設費 / 定常時の営業収支。
- 割引回収年数 = 開業時点に建設費を一括計上し、$\sum_{t=1}^{T} \text{CF}_t / (1+r)^t \ge \text{建設費}$ となる $T$（年の途中は線形補間）。
  割引率 $r$ = 4%（国土交通省の事業評価で用いる社会的割引率）、上限 100 年。
- 営業収支 ≤ 0、または上限までに回収できない場合は「回収不能」。
- 考慮しないもの（UI に注記）: 更新投資、建設期間中の利子、諸税（固定資産税など）、既存線の収支への影響、運行本数と需要の相互作用。

## 9. 既知の限界（Phase 1）

- 急行・直通運転を無視するため、長距離の所要時間を過大評価しがち。
- 新線開業による既存駅の利用減（カニバリゼーション）は Huff で新線側の取り分としてのみ表現し、既存線の収支変化は計算しない。
- 誘発需要（新線による新規トリップ）は外部選択肢 $V_0$ からの転換としてのみ表現。
- S12 の事業者間で計上基準が不統一（乗換客の扱い等）なため、大ターミナルの再現性は低い。
- ポータル間の短絡転換は校正データが無く、パラメータは仮置き。バックテスト（§10）では、この経路転換が TX の過大推計（約 2.6 倍）の主因だった。

```
  routes[]                運行系統 = 列車が走る駅の並び（N02 の法令上の線名とは別。直通先は別の系統として through で結ぶ）

    quality               timetable（時刻表ベース）| published（公表資料ベース）| provisional（仮置き）
    source, frequencySource
    stations[]            stations.json の添字（走行順。方向は対称とみなす）
    cars                  平均編成両数（国交省の混雑率データ。なければ null）
    peakTotalTph          全種別合計のピーク本数（時刻表ベースのみ。国交省の値 mlitPeakTph と照合用）
    through[]             { route: 直通先の系統 ID（無ければ null と operator）, at: 接続駅, share: 直通する列車の割合 }
    services[]            運行種別（各停・快速・急行 …）
      name
      stops[]             停車駅（stations の位置）
      legMinutes[]        停車駅間の所要時間 [分]（停車時間込み）
      tph { peak, offpeak }  片方向の本数 [本/時]（peak = 朝ピーク 1 時間、offpeak = 日中の 1 時間平均）
  lineQuality[]           N02 の線（network.json の lines）ごとの品質（延長が最も長い品質）。UI の既存線の表示に使う
  lineKm[]                線ごとの品質別延長 [km]
```

### 11.2 データの作り方（品質別）

| 品質 | 対象 | 停車駅 | 所要時間 | 本数・編成 |
|---|---|---|---|---|
| 時刻表 | ODPT のオープンデータ（現時点は都営。トークン取得後に東京メトロ・TX・横浜市営・りんかい線・ゆりかもめ・多摩モノレール） | 平日の列車のうち、その種別の列車の 50% 以上が停車する駅 | 停車駅間の所要時間の中央値（両方向まとめて） | 駅・方向ごとの 1 時間の発車本数のピーク（7〜8 時台の最大）と日中（10〜15 時台の平均）。編成は国交省 |
| 公表資料 | JR・大手私鉄の主要系統（`services.yaml` の routes） | 各社公式の停車駅 | 運転曲線の簡易計算（下記） | 国交省の混雑率データのピーク本数 × 種別の割合。日中はピークの比率（仮置き）か公表値 |
| 仮置き | 上記以外の N02 の線 | 全駅停車 | 線路延長 ÷ 表定速度（pipeline.yaml の rail.speed_kmh。Phase 1 と同じ） | 国交省の値があればそれ（品質は仮置きのまま、`frequencySource` に記録）、なければ事業者種別ごとの仮置き値 |

- 直通: 時刻表ベースは列車の始発・終着駅が他事業者の線にあるものを数え、接続駅で他事業者の系統（その駅を含み、事業者名が一致するもの）と結ぶ。公表資料ベースは設定の through で指定する。
- 時刻表の公開範囲: 公共交通オープンデータ基本ライセンスのデータは、元の時刻表を復元できない集計値（種別ごとの所要時間の中央値・1 時間あたり本数）だけを services.json に書き出す。

### 11.3 運転曲線の簡易計算（公表資料ベースの所要時間。M3 の新線にも使う）

駅間距離 $d$、最高速度 $v$、加速度 $a$、減速度 $b$ のとき、加速・惰行なしの定速・減速の台形で走行時間を求める。
$d \ge v^2/2a + v^2/2b$ なら $t = v/a + v/b + (d - v^2/2a - v^2/2b)/v$、届かなければ最高到達速度 $v' = \sqrt{2dab/(a+b)}$ の三角形で $t = v'/a + v'/b$。
所要時間 = (走行時間 + 停車時間) × 余裕係数。初期値は加速度 3.0 km/h/s・減速度 3.5 km/h/s・停車 30 秒（乗換駅 50 秒）。いずれも仮置き。
余裕係数 1.15 は、都営地下鉄 4 線の時刻表の駅間所要時間との比較（最高速度 70〜100 km/h で係数なしの計算に対し 1.10〜1.30 倍、中央値 約1.17）から決めた。

## 13. 一般化費用（Phase 2 M2）

乗車時間・待ち時間・乗換抵抗・アクセス（徒歩）を合成した費用 [分]。Phase 2 の経路転換、Phase 3 の経路選択、Phase 4 の利用者便益で共通に使う。
実装は前処理の `scripts/gencost.py` とブラウザの `src/core/generalizedCost.ts`（同じ式）。パラメータは `scripts/config/demand.yaml` の
`generalized_cost`（校正値とあわせて `demand.calibrated.json` の `generalizedCost` に書き出す）。

$$\text{一般化費用} = T_{\text{乗車}} + w_{\text{待ち}} \cdot T_{\text{待ち}} + \text{乗換抵抗} + w_{\text{徒歩}} \cdot T_{\text{徒歩}}$$

| 項目 | 定義 | 初期値 |
|---|---|---|
| 待ち時間 | min(60 / 代表本数 / 2, 上限)。代表本数 = ピーク × 0.5 + 日中 × 0.5 | 上限 15 分（仮置き） |
| 待ち時間の重み $w_{\text{待ち}}$ | 乗車時間 1 分に対する重み | 1.5（仮置き） |
| 乗換抵抗 | 同一事業者 3 分、他事業者・新線 8 分（乗換の歩行・抵抗。待ち時間は別に数える） | 仮置き |
| 直通運転 | 乗換抵抗・待ち時間とも 0（直通先の系統に乗ったまま進む） | — |
| 徒歩 | 名前の異なる近接駅の徒歩乗換（歩行 4.8 km/h × 迂回 1.3）、駅までのアクセス（Phase 3 で使う） | 重み 1.0（仮置き） |

### 13.1 既存ネットワーク（前処理）

運行データ（§11）から「駅 S ／（駅, 事業者）O ／（系統, 種別, 停車駅）V」のグラフを作り、全駅間の最小の一般化費用を求める（`gencost.build_graph`）。
乗車（O→V）に待ち時間と乗換抵抗の半分、降車（V→O）に乗換抵抗の半分、V どうしは乗車時間、直通する系統は接続駅の V どうしを 0 で結ぶ。
出発・到着の乗降の抵抗（計 8 分）は最後に差し引き、最初の乗車の待ち時間は残す。結果は整数分に丸めて `times.bin` に入れる（Phase 1 の所要時間と同じ形式・同じ使い方。255 分以上は到達不能）。

OD ごとの内訳（乗車・待ち・乗換・徒歩）は、重みに各内訳を微小倍（1e-4）して足したグラフで最短距離を求め直し、増分から求める（経路は変わらない）。
`calibrate.py` が `data/interim/<地域>/gc_breakdown.npz` に保存する（Phase 4 で整備あり・なしを比べる）。首都圏の全駅間の平均は乗車 80 分・待ち 9 分・乗換 15 分・徒歩 0.6 分。

### 13.2 新線（ブラウザ）

既存駅間は `times.bin` の一般化費用。新線は乗るたびに待ち時間（重み × min(60 / 代表本数 / 2, 上限)）を 1 回足す。代表本数は M2 では
`service.representativeTph`（8 本/時、仮置き）、M3 で運行計画の種別ごとの本数に置き換える。経路転換（§4.5 の 2 項ロジット）は式の構造を変えず、
既存経路と新線経由の一般化費用の差で計算する（式の見直しは Phase 3）。

### 14.2 所要時間と需要

- 停車駅間の所要時間は §11.3 の運転曲線の簡易計算（`src/network/runtime.ts`）。交通機関タイプのパラメータ（最高速度・加減速度・停車時間・余裕係数・折返し時間）を使う
  （`src/config/transitTypes.ts`。M3 は普通鉄道のみ: 110 km/h、3.0/3.5 km/h/s、停車 30 秒・接続駅 50 秒、余裕 1.15、折返し 10 分）。
- 需要（`src/demand/lineOperation.ts`）: 新線上の駅の組ごとに、両方に停まる種別の代表本数の合計で待ち時間を、本数で重み付けした平均で乗車時間を求め、
  一般化費用 = 1.5 × 待ち時間 + 乗車時間 とする（来た列車に乗る。途中駅での種別の乗換は扱わない）。本数を増やすと待ち時間が減って需要が増え、経費（車両キロ）も増える。
- 直通運転: 接続駅から直通先の系統の各駅まで、その系統の主な種別の乗車時間で行ける（乗換抵抗・待ちなし）。その先は乗換（他事業者の抵抗）して既存線。
  直通先の系統の時間は services.json から求める（`src/data/services.ts` の `rideTimesFrom`）。
- 運行計画を渡さないとき（バックテストの比較用）は Phase 1 と同じ一律の表定速度・代表本数（`uniformOperation`）で、M2 の結果と一致する。

### 14.3 必要編成数・車両キロ・待避設備（`src/network/servicePlan.ts`）

- 必要編成数（種別ごと）= ⌈ピーク本数 × 往復時間 / 60⌉、往復時間 = 片道 × 2 + 折返し × 2。両数 = Σ 編成数 × 両数 × (1 + 予備率 10%)。直通先を走る時間は数えない（新線内だけ）。
- 車両キロ（年）= Σ（ピーク本数 × ピーク時間 + 日中本数 ×（運行時間 − ピーク時間））× 2 方向 × 営業キロ × 両数 × 365。ピーク時間 4 時/日・運行時間 18 時/日（仮置き）。
- 待避設備（簡易判定）: 速い種別 F と遅い種別 S の組ごとに、S は等間隔（運行間隔 h）、F は前の S の h/2 後に発車すると仮定する。両方が停車する駅で測った
  「F が S より先に進んだ時間」（起点からの所要時間の差）が h/2, 3h/2, … を超えるたびに追いつくので、超える手前の両方が停車する駅に待避設備を置く。上り・下りの両方向で判定し、起点は除く。
  費用は駅の構造別に 1 駅あたり 地平 15 億円・高架 40 億円・地下 120 億円（仮置き）を建設費に加える。

### 15.2 併用軌道（LRT）

軌道運転規則 第53条（e-Gov で確認）: 動力制動機を備えた車両は最高 40 km/h 以下・平均 30 km/h 以下。
併用軌道を含む停車駅間は、最高速度を 40 km/h として運転曲線で求めた時間に信号待ちなどの遅れ（0.5 分/km、仮置き）を足し、
併用軌道の部分の平均速度が 30 km/h を超えないよう下限をかける（`stopToStopMinutes`）。

### 15.3 費用の扱いと警告

- 普通鉄道は費用パラメータ（パラメータ画面）の値をそのまま使う。他のタイプは建設・車両・運行経費の単価と賃率・最低運賃をタイプの値で上書きし、
  用地の地価補正・管理費率・定期の割合・評価の設定などは共通（`effectiveCostParams`）。
- タイプで選べない構造の区間（`invalidStructureSegments`）と、運行計画の警告（ピーク本数の合計が最小運転間隔を超える、編成両数が上限を超える。`planWarnings`）を返す。UI での表示・変更の促しは M6。
- インフラ補助の対象フラグ（モノレール・AGT）は Phase 4 の事業スキームで使う。今は計算に使わない。

## 16. 輸送力制約（Phase 2 M5）

実装は `src/demand/capacity.ts`、パラメータは `src/config/capacity.ts`。

| 項目 | 式・値 | 根拠 |
|---|---|---|
| ピーク 1 時間の断面輸送量 | max(上り, 下り の 1 日の断面輸送量) × 0.15 | 仮置き（首都圏の通勤路線の最混雑区間のピーク 1 時間が 1 日の片方向の 15% 程度という概数。要確認） |
| 輸送力 | Σ 種別（ピーク本数 × 編成両数 × 1 両の定員） | 定員はタイプ別（§15、国交省の混雑率データから） |
| 混雑率 | ピーク 1 時間の断面輸送量 / 輸送力 | 国交省の混雑率の定義と同じ |
| 混雑の不効用 | 新線の乗車時間 × (1 + 0.5 × max(0, 混雑率 − 1.0)) | 仮置き（150% で 1.25 倍、200% で 1.5 倍） |
| 警告 | 150% 超（目標の水準）、180% 超（輸送力では捌けない需要） | 国交省の都市鉄道の混雑緩和の目標（主要区間の平均 150%、個別路線 180% 以下） |

均衡計算: 係数 1 で需要を推計 → 区間の混雑率 → 目標の係数 → 逐次平均法（n 回目は差の 1/(n+1) だけ動かす）で係数を更新 → 需要を推計し直す、を最大 6 回、
係数の変化が 0.01 未満になるまで繰り返す。最初の推計で全区間の混雑率が 100% 以下なら 1 回で終わる（通常は追加の計算なし）。
区間の係数は新線上の駅の組の乗車時間に、距離で重み付けした平均として掛ける（`onLineCost`）。既存線の混雑は扱わない（Phase 3 のネットワーク配分で扱う）。
